# Архитектурный разбор python-agent и план доработки

Дата: 2026-10-06 · Коммит: `5c8094f`

Состояние кода: 45 тестов проходят, `ruff` и `mypy --strict` без замечаний. При этом `.venv`
сломан: шебанги скриптов указывают на старый путь `.../Code/ml/agents/python-agent`, поэтому

## 1. Итог в двух словах

Фундамент хороший: состояние хранится в БД, а не в JSON-файлах, перед побочными эффектами есть
централизованные approvals, ведётся аудит исходящих запросов, PathGuard проверяет пути, Redis-режим
продуман. Это заметно взрослее предыдущей реализации.

Слабое место — **сам агентский цикл и всё, что видит пользователь**: нет стриминга, reasoning
не используется, `finish_reason` игнорируется, контекст сжимается грубо, инструментов для
разработки мало, а UI — техническая заглушка без markdown и без отрисовки tool-calls, с ручным
вводом токена.

| Ось | Оценка | Комментарий |
|---|---|---|
| Персистентность / модель данных | 7/10 | БД и миграции есть; нет индексов по `session_id`, SQLite без WAL |
| Безопасность инструментов | 7/10 | approvals, PathGuard, SSRF-защита; но DNS rebinding в режиме без токена |
| Распределённый режим | 6/10 | продуман, но есть гонка dedupe/ack |
| Агентский цикл | 4/10 | O(n²) загрузка, коллизия ID, Stop не останавливает side effects, child+approval сломан |

| Набор инструментов | 4/10 | нет glob/find, мульти-правок, git, todo/plan; у shell нет `HOME`, нельзя использовать пайпы |

## 2. Что на скриншотах (тёмный UI)

Это **не векторизованные эмбеддинги**. Там два разных блока:

1. **Блок `tool` с сырым JSON** — это результат `list_dir`, который UI выводит как есть
   (`frontend/src/App.vue:289-291`: `<pre>{{ message.content }}</pre>`). Сам вызов инструмента
   (`assistant.tool_calls`) не показывается вообще: в типе `Message` во фронте нет `tool_calls`.
2. **«Исходящие обращения (6)» с SHA-256** — это журнал `outbound_audit` (`App.vue:294-302`).
   Каждый вызов LLM пишет две строки, `started` и `completed` (`runtime.py:271-299`), с хешем
   payload. Это compliance-журнал: «что и сколько байт ушло наружу», без самого текста.

Вывод: в основном чате это действительно мусор. Аудит нужно **оставить на бэкенде**, но в UI
убрать в отдельную вкладку «Приватность / Audit» в правой панели: одна строка на запрос
(`started` и `completed` объединены), с длительностью и токенами, а хеш показывать только по
наведению. Tool-calls нужно отрисовывать карточками, как в светлом макете.

Светлый макет (`2026-10-06 08.32.22.jpg`) задаёт правильную IDE-подобную раскладку. Подробнее в разделе 6.

## 4. Архитектурные слабости и что оптимизировать

### 4.1 Агентский цикл (`runtime.py`)
- На **каждом шаге** через `selectinload` загружаются все сообщения и все tool-calls сессии
  (`runtime.py:208-217`), то есть O(n²) по длине сессии. Нужен инкрементальный загрузчик или кэш
  контекста в памяти на время прогона, а из БД дочитывать только дельту.
- Для каждого LLM-вызова контекст сериализуется в JSON ради SHA-256 аудита (`runtime.py:264`) —
  лишние мегабайты на шаг. Хешировать можно байты, которые реально уходят в httpx.
- Read-only tool-calls выполняются последовательно. Батч `read_file`×5 можно гонять через `asyncio.gather`.
- `emit_event` на каждое событие делает отдельный `commit` и `refresh` (`events.py:115-118`).
- Глобальные синглтоны на уровне модуля (`api.py:45-46`, `database.py:14-16`) мешают тестам и DI.
- Таблица `Command` и поле `Message.skipped` в коде не используются: мёртвые сущности.
- Нет «очереди сообщений»: пока сессия `running`, `POST /messages` отвечает 409. Пользователь не может
  дописать уточнение на ходу.

### 4.2 LLM-слой (`llm.py`)
- **Стриминг SSE**: сейчас пользователь ждёт весь ответ (до 120 с) перед пустым экраном.
- **Reasoning**: `reasoning_content` / `reasoning` выбрасываются, а `reasoning_effort` не передаётся.
  Для DeepSeek в thinking-режиме с tool-calls reasoning, возможно, надо возвращать модели внутри
  одного хода — это нужно проверить на вашем `deepseek-v4-flash`.
- Новый `httpx.AsyncClient` на каждый вызов: нет keep-alive, лишний TLS handshake.
- Retry не учитывает `Retry-After`, нет jitter, нет fallback-профиля, нет circuit breaker.
- Нет учёта usage и стоимости по сессии (`prompt_tokens` никуда не пишется).

### 4.3 Контекст (`context.py`)
- Защищены только первые `system` и `user`, всё старое просто отбрасывается.
- Нужна **ступенчатая компрессия**: (1) маскирование старых tool-результатов, (2) свёртка
  аргументов `write_file`/`edit_file`, (3) LLM-суммаризация старой части с сохранением
  резюме как `Message(kind=summary)`. Плюс **калибровка** по реальному `usage.prompt_tokens`
  (это было в предыдущей реализации).
- Обрезка tool-результата посреди JSON ломает структуру; лучше обрезать поля `content`/`stdout`
  внутри объекта.

### 4.4 Инструменты
Нет того, без чего агент разработчика слаб:
- `glob`/`find_files`, `read_many`, `multi_edit` / `apply_patch` (unified diff), правки по номерам строк;
- `git_status` / `git_diff` / `git_log` как read-only инструменты без approval;
- `todo` / `plan` (агент ведёт чек-лист, а UI его показывает);
- `fetch_url` → markdown (web_search_read);
- **правила автоодобрения**: allow-list команд (`pytest`, `git status`, `npm test`) и режим
  «разрешить для этой сессии». Сейчас каждая запись требует клика, и это главный UX-тормоз;
- shell с опциональным `sh -c` (пайпы, `&&`) за отдельным, более высоким risk level.

### 4.5 API и события
- Объединить `GET messages/approvals/children/audit/context` в один снапшот
  `GET /sessions/{id}/state`; WS сделать **подпиской на сессию** с дельтами
  (`message.delta`, `tool.started`, `tool.completed`, `approval.required`) и resume по `last_event_id`.
- Нужна OpenAPI → TS-генерация типов (сейчас `api.ts` пишется руками и уже расходится со
  схемами: `Message` без `tool_calls`).

### 4.6 Наблюдаемость
- Структурные логи (JSON) с `session_id`/`step`, длительность LLM- и tool-вызовов, токены, ошибки.
- Опционально OpenTelemetry-спаны: шаг → LLM → tool.

## 5. Что взять из предыдущего агента

Предыдущая реализация агента богаче по продуктовым функциям, но слабее по фундаменту: история
в JSON-файлах, запуск workers через `exec()`, shell через строку, LLM-клиент без обработки
ошибок. Переносим идеи, а не реализацию.

### Брать (по приоритету)
1. **Многоуровневое сжатие контекста и калибровка по `usage`.** Сжатие зависит от типа
   инструмента. Пары «assistant + tool» удаляются целиком. Сжатая версия — только проекция,
   оригинал остаётся в БД.
2. **Обработка переполнения контекста:** принудительное сжатие до 60 % окна и не более двух
   повторов.
3. **Обработка `finish_reason=length`:** увеличение `max_tokens` и затем просьба ответить
   короче. Детектор утечки разметки вызовов инструментов DeepSeek (`<｜DSML｜tool_calls>`).
4. **Отрисовка вызовов инструментов в UI:** вкладки Formatted и Raw, отдельные форматтеры для
   правки, записи, чтения и shell.
5. **Пакетные подтверждения:** «Разрешить все», комментарий при отклонении.
6. **Автоодобрение shell по шаблонам.** У нас проверка идёт по `argv`, а не по регулярному
   выражению по строке, поэтому `git status; rm -rf` не пройдёт.
7. **Роли и промпты** с политикой на режим: допустимые расширения файлов и запрещённые
   инструменты. Инструкции проекта (аналог AGENTS.md).
8. **Права папок** «только чтение / чтение и запись» и несколько корней на проект.
9. **UX:** правка прошлого сообщения, повторный запуск, переименование и автоназвание сессии,
   архив вместе с дочерними сессиями, уведомления ОС о подтверждении, подстатус («модель
   думает», «повтор 2»), индикатор набора, сохранение черновиков, дерево сессий.
10. **Инструменты:** правки и чтение по номерам строк (надёжнее для слабых моделей), получение
    определения символа (tree-sitter), чтение другой или дочерней сессии, чтение веб-страницы,
    линтеры и проверка типов через профиль проекта, список доступных подключений к БД и SSH.

### Не брать
- хранение истории в файлах;
- синхронный запуск дочерних агентов через `exec()`;
- shell через строку и автоодобрение по регулярному выражению;
- адреса провайдеров и имена пользователей в шаблоне конфигурации;
- самописный серверный Markdown → HTML: на фронте нужны markdown-it, DOMPurify и shiki.

### Уточнения
- Запись файлов на удалённый хост — через SFTP с allowlist удалённых каталогов и атомарным
  переименованием. Проверка ключа хоста обязательна.
- База знаний: ключевые слова от LLM и два вектора (содержимое и ключевые слова), порог
  близости. Сейчас наша база знаний загружает все документы в память (`knowledge.py:95`).
- Правка прошлого сообщения — через ветвление диалога: оригинал сохраняется, подтверждения
  старой ветки отменяются.
- Черновики — с UUID сообщения клиента и уникальным ограничением на сервере.
- Circuit breaker и fallback в предыдущей реализации были только планом.

## 6. UI: целевой дизайн и аутентификация

### 6.1 Убрать токен из интерфейса
Рекомендация для однопользовательского локального агента с опцией удалённого доступа:

1. **Localhost-режим (по умолчанию):** токена в UI нет вообще. Защита строится на `TrustedHostMiddleware`
   (`127.0.0.1`, `localhost`) и проверке `Origin` для REST и WS. Это закрывает B2 без
   какого-либо ввода.
2. **Удалённый режим (`AGENT_API_TOKEN` задан или bind не на localhost):** при старте сервер печатает в
   консоль **одноразовую ссылку** `http://host:8080/auth/bootstrap?code=<otp>` (как Jupyter).
   Переход по ней ставит cookie `HttpOnly; SameSite=Strict; Secure` (за TLS) с подписанной
   сессией, OTP сгорает, URL очищается через `history.replaceState`. Дальше REST и WS
   аутентифицируются cookie, а JS к секрету доступа не имеет.
3. Заголовок `X-Agent-Token` остаётся для CLI, скриптов и healthcheck.
4. Для мутирующих запросов CSRF закрывается через `SameSite=Strict`, проверку `Origin` и обязательный
   `Content-Type: application/json`.

- Светлая тема по умолчанию (как в макете) и тёмная по `prefers-color-scheme`. Дизайн-токены задаются CSS-переменными.

## 7. Конфигурация моделей: убрать JSON-строку из `.env`

Проблема: `AGENT_LLM_PROFILES={"fast":{...},"reasoning":{...}}` — это одна строка, в которой смешаны
секреты и структура. Её неудобно редактировать и ревьюить, а ошибка в одной запятой валит весь запуск.
Кроме того, `context_window` сейчас глобальный, хотя у разных моделей он разный.

**Решение: отдельный файл `config/models.yaml` для структуры, `.env` только для секретов.**

**Провайдеры (решение от 2026-10-06):** Claude, Codex/GPT, GLM, локальные MLX-серверы и LM
Studio, плюс корпоративный шлюз и Ollama. Типы транспорта:
- `openai` — OpenAI-совместимый `/chat/completions`: корпоративные шлюзы, GLM (`https://api.z.ai/api/paas/v4`),
  LM Studio (`:1234/v1`), `mlx_lm.server` (`/v1`, по умолчанию тоже порт 8080 — конфликт с
  агентом), Ollama (`:11434/v1`);
- `openai_responses` — OpenAI Responses API для Codex/GPT reasoning-моделей; доступ по API-ключу
  OpenAI, а не по подписке ChatGPT, которую использует Codex CLI;
- `anthropic` — Messages API, рассуждения через `thinking.budget_tokens`.
Адаптеры `anthropic` и `openai_responses` — фаза 2. В UI будут пресеты: тип, URL и имя
переменной ключа подставляются автоматически, у локальных серверов ключ не нужен.

```yaml
# config/models.yaml  (в git — models.example.yaml; сам файл в .gitignore либо без секретов)
providers:
  gateway:
    kind: openai            # openai | anthropic | jev
    base_url: https://llm.example.com/v1
    api_key_env: GATEWAY_API_KEY     # имя переменной из .env / Keychain, не сам ключ
    timeout_seconds: 120
    max_retries: 3
  local:
    kind: openai
    base_url: http://127.0.0.1:11434/v1
    api_key_env: null
  typesafe:
    kind: jev
    base_url: https://api.typesafe.ai/v1
    api_key_env: TYPESAFE_API_KEY

models:
  fast:
    provider: gateway
    model: deepseek-v4-flash
    context_window: 131070
    max_tokens: 8192
    reasoning: { supported: true, default_effort: low }
    pricing: { input_per_mtok: 0.0, output_per_mtok: 0.0 }
  deep:
    provider: gateway
    model: <reasoning-model>
    context_window: 131070
    max_tokens: 16000
    reasoning: { supported: true, default_effort: high }

routing:
  default: fast
  fallback: [fast, local]             # при 5xx / circuit open
  roles: { review: deep, arch: deep }  # роль → модель по умолчанию

decisions:                            # см. раздел 8
  enabled: false
  provider: typesafe
  model: jev-latest
```

Реализация:
- `pydantic-settings` + `YamlConfigSettingsSource`, строгая схема (`extra="forbid"`), ссылки
  `provider:` проверяются при загрузке; путь задаётся через `AGENT_MODELS_FILE` (по умолчанию `config/models.yaml`);
- секреты разрешаются через `api_key_env`, опционально через `keyring` (macOS Keychain); в YAML ключей нет;
- `agent config check` — CLI-валидация с понятными ошибками (строка и поле); предупреждение о
  `http://` на нелокальный хост (B24);
- обратная совместимость: `AGENT_LLM_*` превращаются в профиль `default`, `AGENT_LLM_PROFILES`
  продолжает работать с deprecation-warning;
- перечитывание по `SIGHUP` или через `POST /api/admin/reload-config`; в compose файл монтируется read-only;
- **Два слоя: YAML + UI** (решение от 2026-10-06). Итоговая конфигурация = `models.yaml`
  (база) + переопределения из UI (таблицы в БД, общие для API и всех воркеров).
  - При совпадении ID провайдера или модели побеждает UI, **по отдельным полям**: если в UI
    изменён только reasoning, остальное берётся из YAML.
  - UI показывает всё из YAML с пометкой «из файла». Правка создаёт переопределение,
    «Сбросить к файлу» удаляет его.
  - Удаление в UI элемента из YAML — флаг `disabled`, файл не меняется.
  - В UI можно добавлять провайдеров и модели, которых нет в YAML.
  - Маршрутизация (default, fallback, roles) тоже YAML + переопределение из UI.
  - Ключи: в YAML только `api_key_env`. В UI — либо свой ключ (только запись, хранится
    зашифрованным, мастер-ключ `AGENT_SECRET_KEY` в `.env`, видны последние 4 символа),
    либо ссылка на другую переменную окружения.
  - «Проверить подключение»: `GET /models` у провайдера, выбор моделей галочками.
  - Если YAML нет, базой служат старые `AGENT_LLM_*`; JSON `AGENT_LLM_PROFILES` — deprecated.
  - Для каждого поля в UI видно, откуда взято значение: файл, UI или env.
  - Бэкенд слоя (таблицы `llm_provider_overrides` / `llm_model_overrides` / `llm_routing_override`,
    merge, шифрование, API `/api/settings/models`) — фаза 1; страница — фаза 3.

## 8. Интеграция Jev (typesafe.ai)

Jev — это **не чат-LLM**, а «System One»-модель: на вход `state` + типизированные вопросы
(`noul` — да/нет 0..1, `choice` — выбор из вариантов, `score` — шкала 2–10 уровней), на выход
ответ + вероятности + `confidence`. API: `POST https://api.typesafe.ai/v1/systemone`,
`Authorization: Bearer`, модель `jev-latest` / `jev-1.13.0`; Python SDK `typesafe-sdk`
(`AsyncTypeSafeClient.system_one`). Сами TypeSafe прямо пишут, что Jev не заменяет LLM
кодового агента. Он нужен для **быстрых, дешёвых и калиброванных решений внутри агента**.

**Статус:** учётной записи TypeSafe пока нет. Поэтому слой делается провайдер-независимым и
сначала работает на `LLMFallbackEngine` (JSON-mode текущей модели) и эвристиках, а Jev
подключается позже одной записью `kind: jev` в `models.yaml` и ключом `TYPESAFE_API_KEY`.

**Архитектура:** новый слой `agent/decisions/` с протоколом `DecisionEngine`
(`noul / choice / score` → `Decision{value, probabilities, confidence}`) и реализациями
`JevEngine` (httpx, без обязательной зависимости от SDK; SDK — optional extra), `LLMFallbackEngine`
(тот же вопрос через JSON-mode обычной модели) и `NullEngine` (выключено). Все вызовы идут через
`outbound_audit` и network allowlist, по умолчанию слой выключен, как и остальные сетевые возможности.

**Точки применения (по ценности):**
1. **Выбор глубины рассуждений и модели** (`choice`: low/medium/high, fast/deep) по
   сообщению пользователя и состоянию сессии. Это прямо то, что нужно для «глубину выбирать по
   ситуации». При низкой уверенности берётся профиль роли по умолчанию.
2. **Триаж approvals** (`score` риска + `noul` «команда только читает?»). Уверенно безопасное
   в рамках allowlist одобряется автоматически, остальное эскалируется пользователю с
   подсказкой «почему рискованно». **Никогда не ослабляет жёсткие политики:** Jev может только
   поднять вызов до ручного подтверждения или авто-одобрить то, что уже есть в allowlist.
3. **Защита от prompt injection** в tool-результатах (`noul`: «содержит ли текст инструкции,
   адресованные агенту?»). При срабатывании результат помечается, а модель получает предупреждение.
4. **Сокращение набора tool definitions** (`choice` по задаче), чтобы не отправлять в контекст
   30+ схем.
5. **Ранжирование для сжатия контекста и KB** (`score` релевантности старых сообщений и
   документов к текущей задаче) вместо простого FIFO.
6. **Guardrail финального ответа** (`noul`: «утверждает ли ответ, что тесты прошли, без
   подтверждающего tool-результата?»). Если да, агент продолжает работу вместо `completed`.

Ограничения: в Jev уходит `state`, то есть фрагменты кода и диалога. Это отдельный канал
egress, который явно включается в конфиге и виден в Audit. Каждое решение пишется в БД
(`decisions`: вопрос, ответ, confidence, latency, использовано или нет), чтобы потом
калибровать пороги и видеть в UI, почему агент так поступил.

## 9. План реализации

Решение от 2026-10-06: все фазы ведём в одной ветке и коммитим вместе после завершения. Фазы 1 и 2 можно вести параллельно с фазой 3.

### Фаза 0 — гигиена (0.5 дня)
- пересоздать `.venv`, поправить путь в README;
- индексы по `session_id` (миграция 0004), SQLite `WAL` + `busy_timeout` + `foreign_keys=ON` (B13, B14, B18);
- изолированная фикстура БД для интеграционных тестов;
- удалить `Command` / `skipped` либо задействовать `skipped` в фазе 2.

### Фаза 1 — безопасность, аутентификация без токена, конфиг моделей (2–2.5 дня)
- `TrustedHostMiddleware` + проверка `Origin` для REST и WS (B2);
- bootstrap-OTP → серверная cookie-сессия (`HttpOnly; SameSite=Strict`, `__Host-` за HTTPS),
  `/auth/bootstrap`, `/auth/logout`, WS по cookie с проверкой Origin **до** `accept`;
- удалить поле токена из UI; `X-Agent-Token` оставить для CLI;
- B15: запись через `O_NOFOLLOW` и проверку `lstat` (или запрет symlink в целевом пути) плюс атомарный rename;
- B16 и B17: проверять `stop_requested` перед **каждым** инструментом, при Stop инвалидировать
  pending approvals, shell запускать в отдельной группе процессов (`start_new_session=True`) и
  убивать `killpg` при отмене или timeout;
- `config/models.yaml` + `api_key_env` + `agent config check` + per-model `context_window`,
  слой переопределений из UI в БД с шифрованием ключей и API настроек моделей (раздел 7);
  HTTPS или предупреждение для LLM endpoint (B24);
- тесты: rebinding-Host → 400, чужой Origin → 403, cookie-flow, symlink-escape, Stop-между-tools.

### Фаза 2 — ядро агента (3–4 дня)
- B1: ID tool-call = `uuid4`, внешний ID провайдера хранить отдельно для протокола;
  `_step` → `session.inference_steps` в БД;
- B3: дочерний агент с `wait=true` работает как полноценная асинхронная задача; родитель
  получает статус `waiting_child` и возобновляется событием завершения ребёнка (без
  блокировки и с поддержкой approvals у ребёнка);
- B4: dedupe через `SET NX` с удалением **до** запуска цикла плюс повторная постановка в очередь по флагу
  `needs_rerun`; B5: условный `UPDATE ... WHERE status != 'stopped'`;
- LLM-клиент: общий `AsyncClient`, **SSE-стриминг** (`message.delta` в WS), reasoning
  (`reasoning_effort` в профиле, `reasoning_content` в отдельном поле сообщения),
  `finish_reason=length` (эскалация `max_tokens` + «короче»), детектор DSML, `Retry-After` +
  jitter, fallback-профиль;
- контекст: калибровка по `usage.prompt_tokens`, ступенчатое сжатие (маскирование
  tool-результатов → свёртка аргументов → LLM-суммаризация в `summary`), обработка
  context-window-exceeded с повтором;
- параллельное выполнение read-only tool-calls; инкрементальная загрузка истории;
- валидация аргументов по JSON Schema с понятной ошибкой для модели (B22);
- transactional outbox: состояние, событие и enqueue в одной транзакции; курсор `XAUTOCLAIM` (B19, B21);
  после включения `foreign_keys=ON` в фазе 0 гонка archive↔delete даёт `IntegrityError` при
  записи события удалённой сессии (найдено на ревью фазы 0) — закрывается этим же outbox;
- учёт usage и стоимости на сессию;
- **регулировка уровня рассуждений**: `reasoning.efforts` и `default_effort` в профиле модели
  (`models.yaml`), переопределение на сессию и **на конкретное сообщение** (селектор
  `auto / low / medium / high / max` в composer, как в макете). Отдельный уровень для дочерних
  агентов и для внутренних вызовов (суммаризация, автоназвание) — дешёвый `low`. `auto` сначала
  работает по эвристике: роль, длина задачи, ошибки на прошлом шаге, эскалация после
  неудачного tool-call. После подключения Jev решение принимает `choice` с confidence (раздел 8).
  Провайдер-адаптер переводит уровень в нужный параметр: `reasoning_effort`, `thinking.budget_tokens`
  или `enable_thinking`, а для моделей без reasoning параметр не отправляет;
- тесты: approval-before-ACK, crash до и после side effect, двойной запуск, child с approval.

### Фаза «Команда» — пользователи, права, изоляция (после фазы 2, до фазы 3)

Решение от 2026-10-06: агентом может пользоваться команда, а не один владелец. Фаза идёт до
нового UI, потому что интерфейс зависит от пользователей и прав.

- **Пользователи и вход.** Таблица пользователей. Приглашение по одноразовой ссылке вместо
  `agent auth link` для каждого входа. Роли `admin`, `member`, `viewer`.
- **Права.** Доступ к проектам и сессиям по роли и участию в проекте. Опасные действия
  (shell, запись файлов, сеть) одобряет владелец сессии или администратор проекта.
- **Кто что сделал.** `user_id` у сообщений, подтверждений, изменений настроек моделей и в
  `outbound_audit`.
- **Ключи и расходы.** Общие ключи команды или личные ключи пользователя. Расход по людям и
  проектам, лимиты. Основа — учёт попыток из шага 2.6.
- **Изоляция shell.** Песочница ОС из ADR 0005 становится обязательной (`required`) для
  командного режима. Бэкенд для Linux (контейнер или отдельный пользователь ОС на сессию).
  Лимиты процессора, памяти и числа процессов.
- **Один репозиторий — несколько сессий.** Отдельный git worktree на сессию или блокировка
  проекта на время записи.
- **Хранилища.** PostgreSQL и Redis по умолчанию для командного режима; SQLite остаётся для
  одиночного режима.
- **Тесты.** Чужой проект недоступен; viewer не одобряет действия; audit содержит автора;
  shell без песочницы в командном режиме не запускается.

- правая панель: модель и reasoning, контекст-бар, тумблеры инструментов, approvals, дети, audit

- composer: очередь сообщений, outbox-черновики, Stop, редактирование последнего сообщения

### Фаза 3.5 — RAG (4–5 дней, после фаз 2 и 3)

Решение от 2026-10-06. Сейчас есть только база знаний: 5 инструментов `kb_*`, поиск по
ключевым словам или по эмбеддингам в памяти процесса, без индекса и без автоматического
извлечения. Фаза заменяет её полноценным RAG.

- **Загрузка.** Источники: файлы проекта и документы. Нарезка учитывает структуру: код делится
  по функциям и классам (tree-sitter), Markdown — по заголовкам. Переиндексация инкрементальная,
  по хешу файла. PathGuard и блокировка секретных файлов действуют и здесь.
- **Эмбеддинги.** Модель задаётся в `models.yaml` новым типом `embedding`: локально (LM Studio,
  MLX, Ollama) или у провайдера. Каждый вызов попадает в `outbound_audit`.
- **Хранилище.** pgvector для PostgreSQL, sqlite-vec для SQLite. Плюс полнотекстовый индекс
  (FTS5 или tsvector).
- **Поиск.** Гибридный: BM25 и векторы, объединение через reciprocal rank fusion. Затем
  ранжирование; после фазы 4.5 ранжирует Jev (`score`).
- **Подстановка в контекст.** Найденные фрагменты добавляются автоматически, в пределах бюджета
  токенов модели. Ответ содержит ссылки на источники: файл и строка или документ.
- **Идеи из предыдущей реализации.** Ключевые слова генерирует дешёвая модель (`light`). У документа два
  вектора: по содержимому и по ключевым словам.
