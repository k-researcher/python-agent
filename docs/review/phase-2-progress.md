## Сделано

- **2.1 Рассуждения.**
  - Миграция 0007: `messages.kind`, `reasoning_content`, `reasoning_effort`.
  - Модуль `reasoning.py`: выбор уровня (сообщение → сессия → `auto` или модель) и адаптеры

  - `StreamPublisher`: временные события `message.delta`, `reasoning.delta`, `stream.reset`
    каждые 50 мс. Строк в таблице `events` эти события не создают.
  - UI показывает набираемый ответ.
- **B8:** shell получает `HOME`, `USER`, `LOGNAME`.
- Проверки: 340 тестов, `ruff`, `mypy`, сборка фронтенда, живой тест стриминга.

## 2.3 Контекст — часть 1 (модули готовы, связка в runtime — часть 2)

Детали — в `phase-2.3-integration.md`. Каждый модуль покрыт тестами и проходит `mypy --strict`.

- `context_budget.py` — бюджет входных токенов: запас `max(256, 2 %)`, без скрытой нижней границы.
- `context_blocks.py` — неделимые блоки (assistant.tool_calls + ответы) и защищённые блоки.
- `context_compaction.py` — ступени 1–2: маскирование старых результатов и свёртка аргументов.
- `context_summary.py` — запрос сводки, нормализация разделов, детерминированная свёртка.
- `summary_runner.py` — вызов сводки на модели `routing.light` без скрытых повторов.
- `checkpoints.py` — загрузка истории с checkpoint и сохранение checkpoint без дублей.
- `llm_errors.py` и typed `LLMError` — классификация ошибок провайдера; переполнение контекста
  только по коду или списку известных фраз, не по любому HTTP 400.
- `wire.py` — один построитель запроса для оценки, отправки и audit; оценка с учётом tools.
- `token_calibration.py` и `calibration_store.py` — калибровка оценки по фактическому usage,
  хранение в БД с обновлением через CAS.
- Миграция 0008: таблица калибровки, поля checkpoint у сообщений, поля попытки в audit.
- `routing.light` в конфигурации моделей и API настроек.
- Неизвестный usage больше не равен нулю: `prompt_tokens` и `completion_tokens` могут быть `None`.

## Распределение работы

- Изолированные модули с тестами: отдельный git worktree на модуль. Запись — только в файлы
  задачи. Shell — любая команда, но в песочнице ОС `required` (ADR 0005): только папка проекта,
  без сети.
- Каждый дифф проходит ревью до слияния. Если в коде дефектов нет и остались замечания только к
  тестам, их проверка выполняется без нового круга ревью.
- В постановке задачи обязателен чек-лист краевых случаев: некорректные входы и данные из БД,
  порядок, отмена, конкурентный доступ, границы, файлы.
- Интеграция в `runtime.py`, `api.py`, миграции: основная ветка `dev`.
