# ADR 0006: Переносной слой файловых операций для Windows

English version: [0006-windows-file-fallback.en.md](0006-windows-file-fallback.en.md).

## Статус

Предложено. Код написан, но приёмочный прогон на Windows ещё не выполнен. Поддержка Windows
объявляется после него. На macOS и Linux поведение не меняется.

## Контекст

`SafeProjectFS` в `src/agent/safe_fs.py` работает через дескрипторы каталогов: `dir_fd`,
`O_NOFOLLOW`, жёсткая ссылка для эксклюзивной публикации, fsync каталога. Конструктор требует
этих примитивов от среды выполнения. CPython на Windows их не даёт, и конструктор отказывается
работать. Ограничение среды, не файловой системы: NTFS поддерживает жёсткие ссылки.

От слоя зависят `read_many`, `write_file`, `edit_file`, `multi_edit`, `remove_file`,
`apply_patch` и `edit_by_lines`, создание и обновление скиллов. На Windows все они падают с
одной ошибкой. В `run_checks` ошибка поглощается при чтении конфигурации, и пользователь видит
«No project check commands were detected for the requested kind».

Ошибка слоя называла внутренние примитивы агента. Наблюдение из эксплуатации (ноябрь 2026,
один пользователь): модель не связала ошибку с платформой и посоветовала снять несуществующее
«ограничение безопасности Windows» и создать файл вручную.

Реализация на дескрипторах Windows (`ReplaceFileW`, DACL) отклонена: это третий слой с новой
поверхностью ошибок при тех же требованиях к контракту. Переносной слой переиспользует контракт
и общие проверки. К нативному варианту возвращаются, если приёмка выявит недопустимые
ограничения переносного слоя.

## Решение

1. Код: `src/agent/safe_fs.py`. Базовый класс `ProjectFS`, слой `PortableProjectFS` и фабрика
   `project_fs(root)`.
2. Фабрика выбирает слой по возможностям среды. Полная поддержка примитивов POSIX — прежний
   `SafeProjectFS`. Windows — `PortableProjectFS`, если корень лежит на локальном диске с
   NTFS. Другие среды, POSIX с неполной поддержкой и корень вне локального NTFS — явный отказ
   с именем причины. Защита на POSIX автоматически не ослабляется.
3. `ProjectFS` объявляет девять операций слоя и общую проверку пути: корень проекта, запрет
   `..`, абсолютных путей вне корня и путей с секретами. Типы и тексты `MissingFileError`,
   `PathSecurityError` и `ToolError` прежние: откат патча различает их по типам, библиотека
   скиллов — по содержимому.
4. Переносной слой проверяет исходную запись аргумента до любого разрешения пути и отклоняет:
   путь с диском без корня (`C:name`), путь от корня диска (`\name`), UNC-пути и пространства
   имён устройств (`\\server`, `\\.\`, `\\?\`, включая именованные каналы); зарезервированные
   имена устройств (`CON`, `CONIN$`, `CONOUT$`, `NUL`, `PRN`, `AUX`, `COM1`–`COM9`, `LPT1`–`LPT9`
   и надстрочные варианты, без учёта регистра, в том числе с расширением и пробелом перед
   ним); двоеточие в компоненте (потоки ADS); конечные точки и пробелы; хвост короткого имени
   8.3; symlink, junction и другие reparse point — по атрибуту записи
   `FILE_ATTRIBUTE_REPARSE_POINT`.
5. Каждая существующая компонента ниже корня должна совпадать с реальной записью каталога:
   точно или одним вариантом регистра. Несколько вариантов означают регистрозависимый
   каталог, ни одного — псевдоним имени; оба случая отклоняются. Полный путь ограничен так,
   чтобы временный файл остался внутри `MAX_PATH`.
6. Корень разрешается один раз по доверенной конфигурации оператора. Junction в самом корне и
   его предках — зона доверия оператора, как bind mount на POSIX.
7. Запись идёт во временный файл `os.open` с `O_CREAT | O_EXCL | O_BINARY` в том же каталоге:
   запись, `fsync`, закрытие дескриптора, повторная проверка цели, затем `os.replace` (внутри —
   `MoveFileExW` с заменой). Чтение открывается тоже в бинарном режиме.
8. Версия файла — `(st_dev, st_ino, st_size, mtime_ns)`. Она сверяется в трёх точках: запись
   каталога против открытого дескриптора, после чтения и непосредственно перед условной
   заменой или удалением. При недоступном идентификаторе файла условные операции отказываются;
   обычная запись остаётся доступной.
9. Эксклюзивная публикация — полностью записанный и закрытый временный файл через
   `os.rename`: на Windows он отказывает при занятом имени, и готовый файл публикуется без
   перезаписи. На POSIX `os.rename` заменяет цель, поэтому правило действует только в
   переносном слое.
10. Права и метаданные не переносятся. На POSIX `fchmod` обязателен: его отказ прерывает
    замену. На Windows права файла не сохраняются, fsync каталога не выполняется.
11. Слой создают через фабрику `src/agent/tools/builtin.py`, `src/agent/tools/patch_tools.py`,
    `src/agent/tools/check_tools.py` и `src/agent/skill_library.py`. В `read_many` файловый
    слой проверяет путь первым, `PathGuard` после него только нормализует отображаемое имя.
    `run_checks` создаёт слой вне обработчика ошибок конфигурации.
12. Скиллы: `load_skill` и `scan_skills` отказываются от каталога-ссылки или reparse point до
    чтения манифеста; обновление скилла проверяет путь манифеста через слой до чтения. Текст
    манифеста для ревизии и сравнения читается без нормализации CRLF.
13. На Windows парсер `apply_patch` сохраняет конечные точки и пробелы в имени файла
    заголовка, чтобы их отклонил файловый слой. На других системах имя очищается от них, как
    раньше.
14. Гарантия в документах безопасности описана раздельно для POSIX и Windows:
    `docs/security.md`, `docs/threat-model.md` и их английские версии.

В решение не входит и остаётся POSIX-зависимым: импорт ZIP-архива скилла (пишет файлы с
`O_NOFOLLOW`), удаление каталога скилла (отказывается через `shutil.rmtree`), чтение файла
скилла инструментом `read_skill`, песочница shell (ADR 0005) и внешние движки.

## Последствия

- После приёмки инструменты слоя и создание и обновление скиллов работают на Windows для
  проекта на локальном диске NTFS, без настройки системы.
- macOS и Linux работают как раньше: фабрика выбирает прежний слой.
- Отказ слоя называет причину: платформа без слоя или том вне локального NTFS.
- На Windows заменённый файл теряет права, атрибуты и потоки ADS.

## Приёмка

- `tests/unit/test_portable_fs.py` проверяет слой на любой платформе: формы имён Windows,
  ссылки, конфликты, неудачу эксклюзивной публикации, откат `apply_patch`, побайтовый UTF-8,
  лимит длины и проверку корня на имитации Win32.
- Приёмочный прогон на Windows с локальной NTFS ещё не выполнен. Он включает: сессию с
  `write_file`, `edit_file` и `apply_patch`; реальный junction внутри проекта отклоняется;
  коллизия в момент `rename` даёт «File already exists»; при отказе замены цель не меняется;
  манифест скилла с CRLF проходит цикл чтение-обновление через API.

## Остаточные риски

- На Windows проверка компоненты и действие разнесены во времени: между `lstat` и операцией
  компоненту могут заменить ссылкой или junction. Якоря `dir_fd` нет, гонка остаётся.
- Время модификации на NTFS обновляется при закрытии пишущего дескриптора. Изменение файла,
  который другой процесс держит открытым, проверка версии может не заметить.
- Временный файл наследует права родительского каталога при создании, до публикации. Если они
  шире прав исходного файла, содержимое временно доступно шире. Замена сбрасывает
  индивидуальный DACL файла до наследуемого от каталога.
- Проверка реального имени и запрет reparse point проверены только имитацией: короткие имена
  8.3, junction и регистрозависимые каталоги NTFS подтверждает приёмочный прогон.
- В регистрозависимом каталоге NTFS запрос с одним вариантом регистра открывает существующую
  запись в другом регистре.
- `os.replace` отказывает, если цель открыта с ограниченным режимом совместного доступа. Отказ
  даёт ошибку слоя, цель не меняется.
- Жёсткие ссылки неотличимы от обычных файлов на обеих платформах. То же признание для
  песочницы shell — ADR 0005.
- Устойчивость замены после аварийного отключения питания не гарантируется.
