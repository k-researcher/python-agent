# ADR 0002: Redis Streams и отдельные workers

## Статус

Принято. Режим опциональный; embedded runtime остаётся стандартным.

## Решение

В распределённой конфигурации PostgreSQL является источником состояния, Redis Stream
— долговечной очередью сигналов о готовых сессиях, а Redis Pub/Sub — транспортом
эфемерных UI-событий. API не выполняет агентский цикл и tool calls. Workers используют
consumer group и распределённую блокировку на session ID.

## Надёжность

Задание подтверждается в Stream после возврата агентского цикла. Неподтверждённое
задание может быть захвачено другим worker после visibility timeout. Состояния
assistant/tool call сохраняются до следующего внешнего действия, поэтому цикл можно
продолжить после падения процесса.

Tool call со статусом `running` после падения считается неопределённым: runtime пишет
ошибочный tool result и не повторяет операцию. Автоматический retry мог бы повторить
платёж, SQL update, SSH-команду или запись файла; безопаснее запросить новое явное
действие пользователя.

## Компромиссы

- Redis Pub/Sub не является журналом, поэтому источник истории событий — таблица
  `events`; WebSocket служит сигналом интерфейсу перечитать состояние.
- Остановка выполняющейся сетевой операции кооперативная и ограничена её timeout.
- Для multi-process режима SQLite запрещён.
- Exactly-once для произвольного внешнего side effect принципиально недостижим без
  поддержки idempotency key целевой системой.
